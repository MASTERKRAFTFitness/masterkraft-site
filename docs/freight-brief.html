Integration 1 of 3

Rating at checkout

Our website prices delivery server side, in real time, before the customer pays. We never accept a freight price from the browser. Without a rating API, bulky items cannot be sold online.

The requirement most rate APIs miss

We price every order twice. Once at checkout to show the customer, and again on the server at the moment we charge the card. The browser sends us only which service was chosen, never what it cost.

So the same inputs must produce the same price for at least 30 minutes, and your service identifier must be stable enough to redeem on the second call. If your pricing is not deterministic, give us a quote token with a stated lifetime instead. When a re-quote disagrees with the displayed price we fail the order rather than charge a different number, so this costs us sales directly.

How our checkout builds a consignment

These rules are already live for parcel freight and would carry over unchanged:

RuleDetail
One carton per unit Each product ships in its own carton, so three barbells are three cartons. We do not consolidate, because we have no packing data to do it accurately.
Dimensions rounded up Integer centimetres, always up, so a carton is never under declared.
Whole order quotes together If any line cannot be priced we quote nothing. Pricing part of an order and shipping the rest for free is worse than quoting none of it.
Two options shown The cheapest service, plus the fastest one that beats it on transit. Enough choice to sell an urgent order without turning checkout into a rate table.
Typed failure reasons We show the customer a different message for "outside network" than for "too large to carry", so we need a coded reason rather than an empty result.
Consignment level pricing preferred If you can price a whole multi-carton consignment in one request, say so. Per carton calls are workable but slower.

Status callbacks

A webhook per status change, carrying consignment_number, order_number, a coded status, a timestamp and a human readable description. Please supply the full list of status codes you can emit, not a sample, since we map them onto Unleashed.

Authentication and environments

  • Server to server API key or OAuth client credentials. No browser calls.
  • Separate sandbox and production credentials.
  • Sandbox must be able to return failure cases, not only successes, so we can build the "cannot quote" path deliberately.
  • Your rate limits. We call rating once per checkout view, so volume is low, but we do not want to find a limit in production.

Alternative

If you have no rating API

We can work with a static rate card while an integration is scoped. To be usable it has to be complete enough to compute a price without a phone call:

  • Zone matrix by destination postcode range, from origin 3074.
  • Weight breaks up to and beyond 600kg.
  • A cubic conversion factor, stated explicitly. Much of our range cubes out before it weighs out.
  • Minimum charge, fuel levy basis, and how often it moves.
  • Surcharges as separate figures: tailgate, residential, two person, remote area.
  • Oversize rules: the length at which an item stops being standard, and what happens then.

We would implement that as a lookup in our checkout.

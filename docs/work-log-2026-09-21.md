## Shipped

### 1. The spec table moved to Supabase (`cf09716`)

The four attributes were meant to live in Unleashed. They cannot, and the reason
is structural rather than unfinished work:

- **`AttributeSet` is read-only on the API.** Products supports GET and POST;
  `AttributeSet` is in the GET response fields and not in the POST request
  fields. The only route in is the browser CSV import.
- **The API cannot read the values back either.** All 1,648 products return
  `AttributeSet: null`; `Products/{guid}/Attributes` 404s. A filled ERP could
  never feed the website.
- **An attribute caps at 50 characters** and the import aborts the whole file on
  the first row over. 19 warranties are longer.
- **69 products with copy have no ERP record** to attach an attribute to.

So `product_content` gained seven columns: 414 rows, 390 assembled sizes, 386
gross weights, 379 warranties, every one unabridged.

The `Product Detail` attribute set turned out to already exist in Unleashed,
created by michael@masterkraft.com on **4 September** — the same day
`reports/erp-copy.md` was generated. The repo had no record of it. The values
import had been attempted and **aborted at row 12 of 328**, which is why the ERP
still holds none of them.

### 2. A parity gate, written before the flip (`bb11b28`)

`npm run check:specs`. 414 products, **2,494 values compared, 2,494 identical**,
LOST 0, CHANGED 0, no missing rows.

It cannot catch a parser bug — both sides run the same parser — and does not
claim to. What it rules out is everything between the parser and Postgres and
back: truncation of the 146-character warranty Unleashed refused, the `×`
surviving the round trip, a null where a value should be. Those were the real
risks of moving the data.

### 3. The page reads specs from Supabase (`113ffc9`)

Prose and specs now follow different rules, and the asymmetry is the change:

| | |
|---|---|
| **Prose** | only a human-edited row wins, as before |
| **Specs** | every row wins, loader-owned included |

Prose has a third source and specs do not. `product-copy.json` holds copy
improved by hand after the load, so a loader-owned row preferred over it would
reinstate the duplicate descriptions that file exists to fix.

`resolveSpecs` merges the row **over** the snapshot rather than replacing it, so
a null column falls through. The worst a bad row can do is state something
stale; it can never render a shorter table.

### 4. A revalidation route (`3081ac7`)

`product-content` is cached an hour and nothing dropped the tag, so an editor saw
no change for up to an hour. Found the hard way: the first render after writing a
test value showed nothing, which looked like the flip had failed. It had not —
`unstable_cache` persists into `.next/cache` and survives a dev-server restart.
Deleting `.next` was the only way to see the change, and production has no
equivalent of that.

Drops tag **and** paths, both, every time, following `api/opinly/route.ts`'s
note. Includes `/merchant-feed.xml`, the second consumer of this copy.

### 5. WooCommerce's own description fields (`49d7c12`)

The spec table had moved but the **meta description** had not.

Measured across the 428 live products:

| field | served by the snapshot | overridden |
|---|---:|---:|
| `short_description` | **385** | 8 |
| `description` | 2 | — |

`short_description` appears under the price **and** is the page's meta

Four levels now, and the order is the contract: a human-edited overview, then
`product-copy.json`, then the row's WooCommerce description, then the snapshot.
Level three sits below the JSON deliberately and above the snapshot deliberately.

## What the day found

**1,313 of 1,641 sellable ERP products have no specs at all.** WooCommerce only
ever held specs for ~390 products; the ERP catalogue is four times larger. Broken
down: 484 Mixed Implements, 363 Weightlifting, 143 Apparel, 88 Strength. This is
a content project, not a migration one — and it is now a data-entry job rather
than an engineering one, because a row is all it takes.

**Six products answer to "functional trainer"**, and at least two are entirely
different machines — one 97.8 kg, one 414 kg. Four have a price of 0.00. Names in
this catalogue are not reliable identifiers; anything copying specs between SKUs
should key off a supplier model number.

**Unleashed rejects a group/sub-group pairing its own hierarchy allows.**
`ProductGroups` reports `Cable Machines` (`d072dabf…`) as a child of `Clearance`
(`bb78bbb2…`), which is exactly the pairing `OSCMDU01` carried, and the POST
validator refused it. Three separate groups are named `Cable Machines` — one
under Clearance, one under another parent, one top-level — which is the likely
cause and is worth cleaning up.

**`CONTENT_REVALIDATE_SECRET` was set in Vercel the whole time.** The deployment
id never changed across the entire episode, so nothing was ever stale.

## What went wrong

**Answered about the wrong product for most of the session.** "The functional
trainer" was matched to `MSCMDU01` because it was the only snapshot hit.
`MSCMS02` is not in the snapshot, so that search was structurally incapable of
finding it. A name that generic warranted checking the ERP for collisions before
answering.

**Measured on the wrong branch and reported the exact inverse.** This working
directory was switched to `blog-cdn-namespace` mid-session by a parallel session.
A dependency measurement run there reported "0 values from Supabase, 2,494 from
the snapshot" — against code predating the flip. The true figure was 390 pages
and 2,494 values, none falling back.

**Copied the Pro's specs onto `MSCMS02` on an assumption.** 414 kg, 454 kg and
2,070 mm went onto a live page on the strength of "same size, different finish".
They are different machines. Caught, cleared and revalidated within minutes, but
a wrong declared weight feeds freight quotes.

**Triggered Vercel's bot mitigation.** ~100 polling requests over 17 minutes plus
dozens of manual `curl`s produced `x-vercel-mitigated: challenge` on every
scripted request. Real visitors were unaffected — a browser solves the challenge
— but it was avoidable and it briefly looked like an outage.

**Sent the secret through a rotation and redeploy that was never needed.** The
`401`s were a wrong generated value, not a stale environment. The build failure
it was pinned on was real but unrelated.

**Wiped `ProductSubGroup` on `OSCMDU01`.** `POST /Products` replaces the whole
record; omitting a field clears it, and omitting the sub-group was what finally
got past the validator. The UI cannot restore it because the dropdown does not
offer it. The price change was the instruction; the UI was the right instrument
and should have been recommended.

**Two pieces of SQL that could not work.** A one-block test where the `UPDATE`
and the response `SELECT` shared a transaction, so `pg_net` had not dispatched
when the read ran. And a trigger whose `WHEN` clause referenced `NEW` across
`INSERT OR UPDATE OR DELETE`, which Postgres rejects at creation — the function
body already branched on `TG_OP` for exactly that reason.
